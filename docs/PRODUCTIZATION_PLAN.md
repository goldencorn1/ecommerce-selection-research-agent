# 电商选品研究产品化推进规划

> 目标：先把“交互式 Web 界面 + 可执行研究报告”打磨成可稳定演示、可解释、可复用的个人项目产品，再接入更复杂的真实商业数据与商业化能力。

## 一、阶段目标

当前项目不以“接入更多数据源”为第一优先级，而以用户拿到报告后能否理解、判断并采取下一步行动为核心验收标准。

产品化完成的最低标准：

1. 用户可以一键启动 Web 页面并完成一次选品研究。
2. 用户可以输入品类、客群、价格筛选区间、研究模式并看到明确的加载状态。
3. 报告必须区分搜索筛选条件、候选价格带、证据来源和不确定性，不能把 Mock 数据伪装成真实商业数据。
4. 每个推荐方向都要有定位、目标人群、价格依据、评分解释、验证动作和风险提示。
5. 报告结论必须给出“现在能做什么、还缺什么证据、下一步如何验证”，而不是只给一个分数。
6. 历史报告、回放、对比和 Excel 预览等已有功能可以被稳定演示，并有错误提示和空状态。

## 二、产品化路线

### 阶段 1：产品定位与报告标准（当前阶段）

- 明确产品是“选品研究与验证决策工作台”，不是自动替用户做采购决策。
- 固化报告结构：结论摘要、推荐方向、价格依据、证据详情、风险、不确定性、验证计划。
- 固化数据标识：Mock、搜索代理、真实来源、用户上传数据分别展示。
- 为不同品类建立可解释的产品画像和推荐变体，避免不同品类输出同质化。
- 增加报告质量验收规则：价格差异、方向差异、证据数量、来源质量、行动建议完整性。

### 阶段 2：Web 信息架构与核心流程

- 首页：研究任务输入、模式选择、数据源说明、最近报告入口。
- 研究过程：阶段进度、搜索状态、模型状态、错误重试、耗时与成本摘要。
- 结果页：先给决策结论，再展开推荐、价格、证据、风险和验证计划。
- 数据页：Excel 上传、字段映射、预览、校验结果和导入范围说明。
- 历史页：报告列表、筛选、回放、删除/归档策略和报告指纹。
- 对比页：多品类或多次运行的指标对比、证据覆盖和结论变化。

### 阶段 3：报告产品化

- 把“推荐”改造成可执行的验证卡片：假设、目标人群、价格、验证动作、成功阈值。
- 为每个价格带展示价格锚点、样本数量、来源类型和置信提示。
- 将总分拆成需求、竞争、差异化、可交付性、风险等子分数，并展示扣分原因。
- 增加“不能据此做出的决定”提示，防止用户把 Demo 结论当作真实采购建议。
- 支持 Markdown、JSON、HTML 快照导出，并确保中文编码和报告指纹稳定。
- 形成至少 3 个演示场景：平板电脑、可折叠露营桌、一个完全不同的品类。

### 阶段 4：交互体验与视觉完善

- 统一视觉语言：研究工作台、证据卡片、风险提示、状态徽章和图表颜色。
- 增加空状态、加载骨架、失败重试、局部失败提示和长任务取消入口。
- 避免信息堆叠：首屏只展示决策所需内容，详情按证据层级渐进展开。
- 在移动端和窄屏窗口下验证表格、卡片、上传区和报告阅读体验。
- 保留无 Node/前端构建环境时可用的本地回退界面，确保一键启动仍然可靠。

### 阶段 5：质量、测试与演示交付

- 单元测试：价格锚定、价格带差异、评分边界、证据质量和报告序列化。
- 集成测试：Mock、搜索、DeepSeek、Excel、历史、回放、对比和错误路径。
- 端到端演示：一键启动、提交任务、等待结果、查看报告、回放和导出。
- 建立固定演示数据和截图/快照，避免外部搜索结果变化导致演示失效。
- 记录已知限制：无真实销售、成本、转化、退款、库存、平台费和合规数据时，只能输出验证优先级。

### 阶段 6：真实搜索与商业数据（后续阶段）

- 继续完善搜索结果清洗、价格抽取、来源质量评分和去重。
- 支持用户上传 Excel/CSV，提供字段映射、类型校验、异常行报告和可追溯导入。
- 在数据模型中区分外部公开证据、用户私有数据和模型推断，禁止无依据混合。
- 再评估数据库、用户系统、云部署、权限和任务队列；这些不是当前 Demo 产品化的前置条件。

## 三、每阶段验收清单

| 维度 | 通过标准 |
| --- | --- |
| 可运行性 | 新环境按文档即可启动并完成一次完整演示 |
| 可解释性 | 每个重要结论都能追溯到证据、规则或明确的模型推断 |
| 差异化 | 不同品类和不同方向的价格带、评分、验证动作不会机械复制 |
| 可执行性 | 用户能从报告中得到明确的下一步和成功/失败判断条件 |
| 诚实性 | Mock、搜索代理和真实数据不会混淆，缺失数据会显式降级 |
| 稳定性 | 外部 API 失败时有可理解错误和可用的降级路径 |
| 演示性 | 能在本地一键打开 Web，并展示历史、回放、对比和导出 |

## 四、当前明确不做

- 暂不把 Mock 结果包装成真实商业结论。
- 暂不为了“看起来像产品”提前引入云部署、数据库集群和用户系统。
- 暂不盲目复制 GitHub 项目代码；只借鉴信息架构、状态设计、证据呈现和工程组织方式，并在落地前检查许可证。

## 五、下一步执行顺序

1. 完成 GitHub 相似项目与 Agent Skill 调研，形成可落地的改造清单。
2. 对照验收清单检查当前 Web 和报告，补齐首屏决策、加载状态、错误提示和报告详情。
3. 固化三类演示场景与回归快照，确保价格带和方向差异可重复验证。
4. 再进入真实搜索清洗与 Excel 商业数据导入的增强阶段。
