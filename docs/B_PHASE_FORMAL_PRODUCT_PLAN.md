# B 阶段正式产品化与展示计划

版本：B0 规划版
日期：2026-08-17
前置状态：A0—A5 已完成，Docker Compose、前后端联调和 Mock 演示已通过。

## 一、B 阶段总目标

B 阶段不是单纯美化网页，而是把当前可运行的 A 阶段验证版收口为一个能够使用真实模型、真实搜索、多品类研究、结果对比和稳定演示的“电商选品研究与验证决策工作台”。

B 阶段完成后，系统必须同时满足：

1. Mock 模式可离线稳定演示；
2. Live 模式可调用真实搜索源，并展示来源、时间和失败状态；
3. DeepSeek 或其它已配置模型可通过预检、实际调用和结果状态验证；
4. 一次任务可以研究多个品类或多个方案，并支持横向比较；
5. 报告仍然遵守 V1 schema、五大报告板块、证据追溯和质量门禁；
6. Web 页面可以完成输入、运行、查看、对比、回放和导出；
7. Docker Compose 一键启动后，可以按固定演示路径完成全流程展示；
8. 演示材料能够诚实区分 Mock、搜索代理、私有数据、真实来源和模型推断。

## 三、阶段路线

### B1：真实模型与真实搜索能力收口

#### 目标

让用户能够清楚知道当前使用的是 Mock、真实搜索还是哪一个真实模型，并且每条真实路径都能被实际验证。

#### 主要工作

- 建立统一的 model/provider registry，不再把模型选项硬编码为 Mock/DeepSeek 两项。
- 增加能力接口，例如模型列表、搜索源列表、是否配置、是否可达、支持能力和当前限制。
- 增加模型和搜索源 preflight，不以“存在 API Key”直接代表服务可用。
- 完成 DeepSeek 真实调用 smoke test，记录模型名、成功/失败状态、token usage、耗时和成本状态。
- 明确 DeepSeek 的职责：规划、归纳、报告表达或审核分别由哪一层负责；所有事实仍必须绑定证据。
- 保留结构化报告和质量门禁，模型失败时只能显式降级，不得伪装为成功。
- 为其它兼容模型预留配置路径，至少支持配置后可发现、可预检、可调用和可记录状态。
- 增加搜索源状态和证据元数据：来源 URL、来源类型、采集时间、搜索查询、质量标识。

#### 产出

- `GET /api/ecommerce/capabilities` 或等价能力接口；
- 模型/搜索源注册表和配置说明；
- DeepSeek 真实调用脱敏记录；
- Live 搜索来源和错误状态字段；
- 模型与搜索预检按钮及前端状态卡片；
- Mock、Live、Live+DeepSeek 三条路径的集成测试。

#### 验收门槛

- 未配置真实服务时，Mock 仍能完整运行；
- 配置正确时，DeepSeek 至少有一次真实成功调用和 usage 记录；
- 配置错误、网络失败、额度不足时，页面显示明确原因和降级状态；
- 报告中不能把 Mock 或搜索摘要写成已验证的销量、利润或市场事实；
- 真实调用失败不影响结构化 schema 和离线演示。

### B2：多品类、多任务和真实数据能力

#### 目标

解决“一次只能搜索一个”的产品限制，让系统具备实际研究工作流，而不是单次 Demo 生成器。

#### 主要工作

- 扩展输入协议，支持单品类、多个品类、多个候选方案和 CSV/Excel 批量导入。
- 支持每个品类独立配置预算、客群、市场和研究约束。
- 增加批量任务队列、并发上限、单项状态、重试、取消和失败重跑。
- 支持多品类统一指标比较：需求、竞争、价格、机会、风险、证据覆盖和推荐置信度。
- 将当前四类研究模块扩展为可配置查询计划，允许不同品类使用不同搜索词和数据源。
- 完善价格抽取、去重、来源质量评分和价格锚定；区分搜索筛选价格与候选推荐价格。
- 接入用户上传的商品库/价格表，并保留字段映射、导入批次和数据来源。
- 在有合规凭据时接入商品/价格/榜单 API；没有凭据时必须显示为“未接入”，不得伪造实时数据。
- 保持单品类接口兼容，批量能力通过新字段或新任务接口扩展，不破坏 V1 schema。

#### 产出

- 批量研究请求与任务状态 schema；
- 批量任务 API、并发和失败重试策略；
- CSV/Excel 导入、字段映射和校验结果；
- 多品类比较报告；
- 至少三类演示数据：可折叠露营桌、平板电脑、完全不同的第三品类；
- 真实数据和模型推断的来源标识。

#### 验收门槛

- 一次提交至少 3 个品类，能够独立完成、部分失败可见、最终汇总可比较；
- 单个品类失败不会丢失其它已完成结果；
- 每个候选方向都有独立价格依据、证据和验证动作；
- 批量任务能够在前端看到进度、失败原因和重试入口；
- 真实数据缺失时仍可切回 Mock，但报告必须显式标记数据类型。

### B3：Web 研究工作台重构

#### 目标

把当前验证页面升级为用户可以理解和操作的正式产品界面。

#### 主要页面与流程

1. **首页/新建研究**：品类或批量文件、市场、客群、价格、研究目标、模型和数据源选择。
2. **能力状态区**：展示 Mock、搜索源、模型的配置状态、可达状态、限额和当前风险。
3. **任务过程页**：展示任务队列、四类分析模块、搜索状态、模型状态、耗时、成本、重试和取消。
4. **结果总览页**：先展示结论、推荐方向、价格带、置信提示和下一步验证动作。
5. **证据详情页**：展示查询、来源、采集时间、证据片段、来源质量和未覆盖项。
6. **多品类比较页**：比较推荐分数、价格、证据覆盖、风险和验证成本。
7. **历史与回放页**：查看历史报告、重新打开、回放、归档和比较；回放不重复调用外部服务。
8. **数据导入页**：上传 Excel/CSV、字段映射、预览、错误行和导入范围。
9. **导出页**：支持 JSON、Markdown、HTML，后续再增加 PDF。

#### 交互要求

- 任何外部服务调用都要显示当前状态，不允许静默显示 Mock 结果；
- 加载、空数据、局部失败、全部失败、超时和重试都要有明确界面；
- 长报告采用“结论优先、证据渐进展开”；
- 桌面端和窄屏窗口均可完成核心流程；
- 继续保留一键启动和前端回退界面，避免正式演示依赖单一运行环境。

#### 验收门槛

- 新用户无需阅读源码即可完成一次单品类研究；
- 新用户无需刷新页面即可完成一次批量研究并查看汇总；
- 失败状态、数据来源和模型状态均可理解；
- 历史、回放、比较和导出均可在 Docker 启动环境完成；
- 浏览器控制台无未处理错误，主要页面无阻塞性布局问题。

### B4：真实评测、可观测性与质量证明

#### 目标

让“正式达到方案要求”有数据支撑，而不是只依靠页面和口头演示。

#### 主要工作

- 固定 50 条评测集和版本号，分别运行 Mock、Live、DeepSeek、Live+DeepSeek。
- 完成 LLM-as-Judge 接入和 20% 人工抽检校准，记录一致性、分歧和修订理由。
- 记录每次请求的节点耗时、搜索调用、模型调用、token、成本、重试、降级和最终质量门禁。
- 接入 Langfuse；如果运行环境不允许，提供等价的本地 JSONL/SQLite 全链路导出，并明确说明边界。
- 输出成功率、证据覆盖率、结构化通过率、P50/P95/P99 延迟、单任务 token 和成本。
- 补做真实模型与真实搜索的回归，不能用离线 Mock 结果代替真实指标。
- 固定两组消融：有/无 Rerank，有/无重试/降级，保留原始结果和配置。

#### 验收门槛

- 50 条评测可重复运行并生成版本化结果；
- 至少 10 条人工抽检记录可追溯；
- 真实调用的 token、耗时和成本状态明确；
- 所有性能数字注明运行环境、模型、搜索源和数据版本；
- 任一外部服务失败时，质量报告能区分失败、降级和成功。

### B5：正式运行、演示与交付收口

#### 目标

形成可重复启动、可重复操作、可重复讲解和可复核的最终版本。

#### 主要工作

- 固定 Docker Compose 生产演示配置和脱敏 `.env.example`。
- 提供 Mock 离线演示包，确保没有 API Key 时仍可完整展示主流程。
- 提供 Live/DeepSeek 可选演示配置，并在启动页显示外部依赖状态。
- 固定一条 3—5 分钟主演示路径：新建任务 → 真实/Mock 模式选择 → 多品类研究 → 进度 → 结果 → 证据 → 比较 → 导出。
- 准备异常演示：搜索失败、模型失败、局部任务失败、回退 Mock 和人工核验提示。
- 完成产品设计说明书、PRD、架构图、Agent 分工图、数据流图、评测报告和用户操作手册。
- 录制演示视频并准备项目截图、精选报告和最终提交包。
- 更新交接文档、版本号、变更记录和已知限制。

#### 最终验收

在全新环境执行以下流程应成功：

```text
启动 Docker Compose
  → 打开 Web 工作台
  → 检查能力状态
  → 输入 3 个品类或导入批量文件
  → 运行 Mock 或 Live + DeepSeek
  → 查看任务进度和局部状态
  → 查看五大报告板块与证据
  → 比较多个品类
  → 回放历史报告
  → 导出报告
```

最终版本必须同时通过：

- 全量自动化测试；
- Mock 离线演示；
- Live 搜索实测；
- DeepSeek 或选定模型真实调用实测；
- 多品类批量实测；
- Docker Compose 启动和健康检查；
- 浏览器端到端测试；
- 50 条评测与人工抽检；
- 文档、视频和交付材料核对。

### B6：网页设计美化与交互体验收口

#### 目标

在不破坏现有 API、V1 schema、Mock/Live 兼容和 Docker 启动方式的前提下，把电商页面升级为具有明确视觉层级、完整任务交互和流畅动画的正式研究工作台。

#### 设计原则

- 采用“研究工作台”而不是单纯聊天页或数据大屏：用户始终知道正在研究什么、依据是什么、下一步做什么。
- 结论优先、证据渐进展开：首屏展示决策摘要，详情页展示来源、查询和不确定性。
- 保持数据诚实：Mock、真实搜索、用户上传数据和模型推断使用不同颜色、标签和状态。
- 优先复用当前 Next.js、Tailwind、Radix UI、Lucide、Framer Motion 和已有 UI 组件，不整体复制外部项目。
- 动画服务于状态变化和空间关系，不使用影响阅读、操作和无障碍的装饰性动画。

#### 页面结构

1. **研究首页**：欢迎区、最近任务、能力状态、快速新建任务。
2. **新建研究页**：单品类/批量品类、市场、客群、价格、模型、搜索源和数据文件配置。
3. **任务运行页**：左侧任务列表，中间阶段时间线和进度，右侧来源/模型/成本状态。
4. **报告页**：摘要、推荐方向、价格带、证据、风险与验证计划五大板块。
5. **比较页**：多个品类或方案的指标、价格、证据覆盖、风险和下一步动作对比。
6. **历史页**：回放、再次研究、归档、筛选和报告指纹。
7. **数据与设置页**：Excel/CSV 导入、字段映射、模型预检、搜索源预检和运行限制。

#### 交互与动画验收

- 页面切换使用统一的淡入/位移动画，动画时长建议为 160—240ms；
- 卡片展开、证据抽屉、筛选器和对比面板使用可逆的高度/透明度过渡；
- 研究阶段使用明确的 pending/running/success/partial/error 状态动画；
- 任务提交后按钮进入防重复提交状态，任务完成后提供结果跳转和导出入口；
- 支持暂停、取消、重试、局部失败查看和失败后继续查看已完成结果；
- Tab、选择器、抽屉、弹窗和键盘焦点行为保持一致；
- `prefers-reduced-motion` 开启时自动降低或关闭非必要动画；
- 关键按钮、链接、筛选、切换和导出操作必须有浏览器端到端测试；
- 页面在桌面端、窄屏窗口和 Docker 启动环境下均无阻塞性布局或点击问题。

#### 产出

- B6 GitHub 设计调研和许可证核对文档；
- 设计方向选择记录和页面线框；
- 统一颜色、间距、字体、状态徽章和动画 token；
- 可复用的布局、状态时间线、证据抽屉、比较表和报告卡片组件；
- 页面交互回归测试和 Playwright 流程；
- 设计前后截图及最终演示页面。

#### 验收门槛

- 用户无需阅读文档即可完成“新建任务 → 运行 → 查看报告 → 展开证据 → 比较 → 导出”；
- 页面中的主要点击、切换、展开、返回、重试和导出操作全部可用；
- Mock、Live、模型失败和局部批量失败均有清晰的视觉状态；
- 动画流畅但不影响任务完成速度、阅读和键盘操作；
- 前端构建、类型检查、浏览器交互测试和 Docker 联调全部通过；
- 不直接复制有品牌限制、许可证不清晰或已经归档的外部项目代码。

## 四、建议实施顺序

必须按以下顺序推进，避免先做页面再发现底层能力不足：

1. B1：真实模型、搜索源和能力预检；
2. B2：批量任务、多品类和真实数据来源；
3. B3：围绕稳定 API 重构 Web 工作台；
4. B4：真实评测、观测和指标证明；
5. B5：Docker、演示路径、材料和最终验收；
6. B6：网页设计美化、交互动画和最终体验验收。

## 五、B 阶段完成定义

B 阶段只有在以下条件同时满足时才可以标记为完成：

- 不是只有 Mock 能跑；
- 至少一种真实搜索源和一种真实模型完成实际调用验证；
- 一次任务可以处理多个品类或方案；
- Web 能展示完整任务生命周期；
- 报告五大板块、证据来源和风险边界保持有效；
- 外部服务失败时有可理解的错误和可复现的降级；
- 50 条评测、人工抽检、成本延迟和观测结果可复核；
- Docker 一键启动后可以按固定路径完成展示；
- 网页设计、交互点击、切换动画和无障碍基础行为通过验收；
- 产品设计说明书、用户手册、演示视频和交接文档全部同步更新。

## 六、明确不宣称的内容

即使 B 阶段完成，也不能宣称系统已经拥有真实销量、利润、库存、转化率或采购保证，除非这些数据来自可验证的授权数据源。系统的定位仍然是“研究、筛选和验证决策辅助工具”，不是自动采购、自动下单或盈利保证系统。
